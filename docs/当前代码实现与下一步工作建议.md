## 2. 当前项目定位

当前项目是一个运行在 SAM 内部的 DXF 几何导入插件。

其主要业务目标有两种导入模式：

**Sketch 模式：**
```text
读取 DXF 文件
→ 提取并处理 DXF 几何
→ 转换为 SAM 可创建的数据
→ 在 SAM 中创建草图
→ 刷新场景并反馈导入结果
```

**FiniteElement 模式（已实现并验收通过）：**
```text
读取 DXF 文件
→ 提取并处理 DXF 几何
→ 转换为 FeData（节点+Truss）
→ 调用 SAM Python API 创建 FE Part
→ 在 Viewport 中显示节点和 T3D2 杆单元
```

当前代码已不再处于"只完成插件框架和接口验证"的早期阶段，而是已打通 DXF 到 SAM 的**双模式完整业务链路**（Sketch + FiniteElement），并通过 SAM GUI 提供全部参数配置（包括 FE 模式的 Model/Part 名称）。

相关文件：

`DxfData` 是解析层使用的 DXF 中间数据模型。

当前已经包含的主要几何类型有：

- `DxfPoint`
- `DxfLine`
- `DxfCircle`
- `DxfArc`

该层主要负责：

- 为解析层和转换层提供统一数据接口。

当前数据模型已经能够支撑基础图元、复杂曲线以及块引用处理。

### 4.4 `ConversionEngine`（Sketch 模式）

相关文件：

```text
src/Example1/ConversionEngine.h
src/Example1/ConversionEngine.cpp
```

`ConversionEngine` 负责把解析后的 `DxfData` 转换成适合 SAM 草图创建的 `SamData`。

当前转换规则主要包括：

- POINT 保留为点；
- LINE 保留为直线；
- CIRCLE 保留为圆；
- ARC 离散为线段；
- LWPOLYLINE 转换为线段；
- ELLIPSE 离散为线段；
- SPLINE 离散为线段；
- 对转换后的坐标应用用户输入的 X、Y、Z 参数；
- 记录离散线段与父实体之间的来源关系。

当前坐标处理函数实际执行的是：

```text
输出坐标 = 输入坐标 + base 参数
```

因此，现有界面中的 `Base Point (DXF)` 在代码行为上更接近"平移偏移量"。后续需要明确其产品语义。

### 4.5 `FeConversionEngine` 与 `FeData`（FE 模式）🟢 新增

相关文件：

```text
src/Example1/FeConversionEngine.h
src/Example1/FeConversionEngine.cpp
src/Example1/FeData.h
src/Example1/FeData.cpp
```

`FeConversionEngine` 将 `DxfData` 转换为 `FeData`（节点+Truss 拓扑），与 `ConversionEngine` 平行的 FE 模式转换引擎。

`FeData` 负责节点去重、Truss 拓扑管理和统计。**2026-07-31 优化**：空间索引增加 `m_indexTolerance` 追踪，容差不变时仅追加节点而不重建索引，避免大批量节点插入时的 O(N²) 重复重建。

转换规则：

| DXF 图元 | FE 输出 |
|---|---|
| `POINT` | 单独节点，无单元 |
| `LINE` | 两节点 + 一个 Truss |
| `CIRCLE` | 闭合离散 Truss 链 |
| `ARC` / `LWPOLYLINE` / `ELLIPSE` / `SPLINE` | 离散线段 + Trusses |

特性：坐标偏移、节点合并、零长度过滤、重复 Truss 过滤均已实现。

### 4.11 `Example1PytModule`

相关文件：

```text
src/Example1/Example1PytModule.h
src/Example1/Example1PytModule.cpp
```

该模块是 GUI 和后端业务之间的 Python 命令入口。

当前 `importDxf()` 主流程大致如下：

```text
读取参数
→ 验证文件和容差 + isfinite(baseX/Y/Z) 检查（新增）
→ 创建导入日志
→ 解析 DXF
→ 按 importMode 分流：
   - Sketch → ConversionEngine → SamData → SamBuilder
   - FiniteElement → FeConversionEngine → FeData → PythonFiniteElementBuilder
→ 创建 SAM 草图和图元 / FE Part
→ 提交
→ 输出统计和日志
```

**新增参数**（2026-07-31）：
- `importMode`：`'Sketch'`（默认）或 `'FiniteElement'`
- `modelName`：FE 模式下的 Model 名称
- `partName`：FE 模式下的 Part 名称
- `nodeMergeTolerance`：FE 节点合并容差

**新增验证**（2026-07-31）：在解析前检查 `baseX/Y/Z` 的 `std::isfinite()`，无效坐标在进入 `DxfParser`/`GeometryUtils` 之前即返回失败。

该模块同时负责组织错误处理、导入阶段标记、进度回调和最终反馈。

## 7. 当前主要问题和风险

### 7.1 BLOCK / INSERT 变换组合不完整

当前普通单层 INSERT 的点变换顺序是：

```text
减去块基点
→ 分别应用 X/Y/Z 缩放
→ 应用 XY 平面旋转
→ 加上插入点
```

这个过程可以处理普通平移、旋转和缩放。

但是，嵌套 INSERT 当前通过以下方式组合：

```text
组合缩放 = 外层缩放 × 内层缩放
组合角度 = 外层角度 + 内层角度
组合插入点 = 经过外层变换的内层插入点
```

这种分解参数直接组合的方法不能完整表示所有仿射变换。

当存在以下组合时可能产生错误：

- 外层旋转加内层非均匀缩放；
- 多层非均匀缩放；
- 负缩放；
- 镜像；
- 镜像与旋转组合；
- 理论上产生剪切效果的嵌套变换。

这可能导致导入流程显示成功，但图形的坐标、方向或尺寸错误。

---

### 7.2 块内曲线保留逻辑存在方向和角度风险

为了减少离散线段数量，当前代码在判断 XY 缩放一致时，会尝试保留 ARC、LWPOLYLINE、ELLIPSE 和 SPLINE 类型。

这种优化目前存在以下风险：

#### ARC

ARC 中心会应用 INSERT 变换，但保留 ARC 时起止角没有同步叠加 INSERT 旋转角。

因此，旋转块中的圆弧可能出现位置或方向错误。

#### CIRCLE 和 ARC 的负缩放

当前保留圆和圆弧时，半径直接乘 `scaleX`。

双轴负缩放时可能得到负半径，进而导致实体被跳过或失效。

#### ELLIPSE

ELLIPSE 中心经过完整点变换，但主轴向量当前只应用缩放，没有应用 INSERT 的旋转。

因此，旋转块中的椭圆主轴方向可能错误。

#### LWPOLYLINE

顶点会被变换，但镜像会改变曲线方向，bulge 符号应根据变换方向进行调整。当前代码没有明确处理这个问题。

#### SPLINE

控制点和拟合点经过变换，但切向量和复杂有理样条在镜像、非均匀缩放下是否保持正确，需要进一步验证。

---

### 7.3 用户取消后可能继续创建并提交

`SamBuilder::createPoints()`、`createLines()` 和 `createCircles()` 在用户取消时返回 `-1`。

当前上层调用方式是：

```cpp
created += builder.createPoints(...);
created += builder.createLines(...);
created += builder.createCircles(...);

if (!builder.commit()) {
    builder.rollback();
}
```

这里没有在每个创建阶段之后立即检查返回值。

可能发生以下情况：

1. 用户在创建 POINT 时取消；
2. `createPoints()` 返回 `-1`；
3. 程序继续创建 LINE；
4. 程序继续创建 CIRCLE；
5. `created` 只是减少一，不一定小于零；
6. 程序仍可能提交草图。

这会使"取消导入"的用户操作与实际结果不一致，也是大文件导入时的重要稳定性风险。

---

### 7.4 POINT 被计为成功但没有真正创建

`SamBuilder::createPoints()` 当前没有调用 SAM 点创建接口。

其主要逻辑是：

```cpp
// TODO: skcGeomFactory::CreatePoint interface TBC
++count;
```

因此，POINT 会：

- 被解析；
- 被转换；
- 被加入 `SamData`；
- 被计入创建数量；
- 出现在日志统计中；

但不会真正出现在 SAM 草图中。

这会造成"成功创建数"和"模型实际对象数"不一致。

### 7.5 Base Point 的界面名称与代码行为不一致

界面名称是：

```text
Base Point (DXF)
```

但转换代码执行的是：

```text
输出坐标 = DXF 坐标 + 输入值
```

因此，这三个参数当前更像平移偏移量。

需要明确三种可能的产品语义：

1. 输入 DXF 基点，并把该点移动到 SAM 原点；
2. 输入平移偏移量；
3. 输入 DXF 原点在 SAM 中的目标位置。

在需求语义确认之前，不应只根据变量名修改加减号。


### 7.7 rollback 不是完整数据库事务回滚

当前 `rollback()` 主要执行：

- 删除 `m_factory`；
- 清理活动状态；
- 清零计数。

它更接近创建上下文清理，而不是完整的 SAM 数据库事务回滚。

当前草图在 `commit()` 中才插入仓库，因此大多数创建阶段失败不会留下仓库对象。但是如果提交过程中部分步骤成功、后续场景刷新失败，当前代码缺少按提交阶段恢复状态的机制。

后续需要明确：

- 仓库插入后失败如何删除对象；
- `Replace()` 成功但场景更新失败是否算导入失败；
- 草图所有权在各阶段由谁管理；
- 是否应保留或清理 Undo 状态。

## 20. 本轮性能优化说明（2026-07-31）

本轮优化保持 DXF 导入接口与几何转换行为不变，集中处理真实船舶图纸导入中的两类已知开销：高频 UI 进度回调，以及重复块和复杂曲线处理产生的容器扩容。

### 20.1 Sketch 创建阶段

`SamBuilder::createLines()` 和 `SamBuilder::createCircles()` 原先每创建 1000 个实体就调用进度回调和 `QCoreApplication::processEvents()`。大图中该路径会频繁进入 Qt/SAM 的 UI 调度逻辑。

### 20.5 BLOCK/INSERT 阵列展开算法优化（2026-08-01）

针对 `DxfParser` 中 `expandInsertArray()` 的 INSERT 行列阵列（`colCount × rowCount`）展开路径与 `expandSingleBlock()` 单实例变换路径，在不改变展开坐标结果的前提下做以下算法优化，位置：`src/Example1/DxfParser.cpp`。

#### 优化内容

1. **消除循环内 `InsertInfo` 深拷贝**

   原实现每个阵列实例都执行 `InsertInfo insCopy = ins;`，由于 `InsertInfo` 包含 `std::string blockName`，每个实例都触发一次堆分配 + 字符串拷贝 + 析构释放。

   现改为循环外只拷贝一次，内层循环仅更新 `insertX` / `insertY` 两个 `double` 字段。

2. **增量递推取代逐格旋转乘法**

   原实现每格计算 `col * colSpace`、`row * rowSpace` 再做 4 次旋转乘法和 2 次加法。

   现预计算行列一步增量向量：

   ```text
   colDx = cosA * colSpace;   colDy = sinA * colSpace;
   rowDx = -sinA * rowSpace;  rowDy =  cosA * rowSpace;
   ```

   网格位置退化为一层循环内的纯加法递推，O(N) 次乘加降为 O(1) 初始计算。

3. **阵列级一次性容量预留**

   `expandSingleBlock()` 只按单实例数量预留容量，阵列场景每个实例的 `push_back` 都可能触发 `std::vector` 扩容与整体搬移。

   现按 `实例数 × 块内实体数` 在进入阵列循环前一次预留 `lines` / `points` / `lwPolylines` / `splines` 容量。

4. **退化场景短路**

   - `nCols * nRows <= 1`：直接走 `expandSingleBlock()` 单实例路径，跳过循环与预留逻辑；
   - 该判定同时避免 `std::max(1, ...)` 后仍为 1 的无效阵列开销。

5. **`Transform2D` 仿射矩阵预构建（`expandSingleBlock`）**

   原 `transformPoint()` 对块内每个实体、每个点，在角度非零时都重复调用 `std::cos(ins.angle)` / `std::sin(ins.angle)`，且每点都要先减块基点再做缩放、旋转、加插入点。

   现新增 `Transform2D` 结构，在一个 INSERT 实例内**只构建一次**：

   ```text
   M = R × S   （m00 = cosA*scaleX, m01 = -sinA*scaleY, m10 = sinA*scaleX, m11 = cosA*scaleY）
   t = insert - M × base
   p' = M·p + t
   z' = scaleZ * z + offsetZ
   ```

   - 平移分量吸收块基点，每点不再做减法；
   - 每个点只做 **4 次乘法 + 2 次加法**（原为 3 减 + 3 乘 + 2 三角函数 + 4 乘 + 2 加）；
   - `expandInsertArray` 内层循环对阵列实例递推 `insertX/insertY`，每个实例进入 `expandSingleBlock` 后仍只构建一次矩阵，因此整个阵列只计算 **N 次 cos/sin**（原为 E×N 次）；
   - 保留下原始 `scaleX/scaleY/scaleZ`，供 ARC/CIRCLE/ELLIPSE 保留路径复用。

#### 时间复杂度分析

设：

- `N = nCols × nRows`：阵列实例总数；
- `E`：块定义内实体总数（点、线、弧、多段线、样条等）；
- `L`：块名 `blockName` 字符串长度；
- `d`：嵌套 INSERT 的递归深度。

**优化前复杂度：**

| 项目 | 复杂度 | 说明 |
|---|---|---|
| 几何变换 | O(N × E) | 每实例对 E 个实体做常量次点变换 |
| 字符串深拷贝 | **O(N × L)** | N 次 `std::string` 构造/析构，每次 O(L) 堆拷贝 |
| 坐标系计算 | O(N) | 每格 4 乘 + 2 加 |
| 容器扩容 | 摊销 O(N × E) | 每实例多次潜在 `std::vector` 重分配搬移，常数大 |

**优化后复杂度：**

| 项目 | 复杂度 | 说明 |
|---|---|---|
| 几何变换 | O(N × E) | 主体不变，内部仍为常量次点变换 |
| 字符串深拷贝 | **O(1)** | 只拷贝一次 `InsertInfo` |
| 坐标系计算 | **O(1)** 初始化 + O(N) 加法 | 内层退化为 2 次加法/格 |
| 容器扩容 | O(N × E)，预留后扩容次数为 0 | 阵列级一次预留后，push 均为 O(1)，不再触发重复扩容搬移 |

**综合渐近复杂度：**

- 单层阵列：`O(N × E)`（优化前后同为 O(N × E)，但常数项大幅下降：消除 N 次堆分配与 N × E 次扩容搬移）。
- 含嵌套的 `expandSingleBlock` 递归（外层实例 × 内层实例，深度 `d`）：总实例数为 `N₁ × N₂ × … × N_d`，复杂度为 `O(∏Nᵢ × E)`。本优化对每一层阵列均生效，因此嵌套阵列的常数收益按层叠加。

**浮点误差说明：** 坐标改为逐格加法累加后，行/列方向的舍入误差随格数线性累积（量级约 `O(N × eps × 坐标量级)`）。对常规工程阵列（几十到几千实例）影响在 1e-9 量级可忽略；若未来出现百万格级阵列，可在每若干格用乘法重新校正一次基点。

**遗留可优化点（2026-08-01 已实施）：** `transformPoint()` 每实体重复调用 `cos/sin` 的问题已通过 `Transform2D` 矩阵预构建解决，见本节第 5 条。更大粒度的优化可在 BLOCK/INSERT 坐标级回归测试建立后，结合仿射矩阵整改嵌套变换组合（见第 7.1 / 9.3 节），其中 `composeInsertTransform()` 的"比例相乘 + 角度相加"组合方式仍受非均匀嵌套缩放限制，属正确性问题而非性能问题。

#### 合并后审查（2026-08-01，merge 28ad14d）

远程分支 `budget` 的 `ExpansionBudget` 安全限制与本机 `Transform2D` 优化已合并到 `example-dxf-plugin`（commit `28ad14d`）。审查结论与残余修复：

**审查通过项：**

- `Transform2D` 仿射矩阵优化完整保留，`tf.apply()` 覆盖全部实体路径（POINT/LINE/CIRCLE/ARC/LWPOLYLINE/ELLIPSE/SPLINE/离散线段/嵌套 INSERT 定位）；
- `ExpansionBudget` 正确融入展开链路：`consumeArray()` 在进入阵列前校验单次阵列实例数（≤100000）与累计块实例数（≤100000），`consumeEntities()` 在每个实体/离散段追加前校验累计实体数（≤100000）；预算失败时 `parseFile` 清空 `outData` 并回传错误信息；
- 合并代码引入 RAII `VisitingGuard`，替换原 `visiting.erase()` 尾部清理，修复预算触发的提前 `return` 导致 `visiting` 泄漏的问题（比原实现更健壮）；
- `composeInsertTransform()` 与 `kMaxExpandDepth=32` 深度保护保持原语义。

**审查发现并修复的问题：**

- **阵列级 reserve 内存尖峰**：`expandInsertArray()` 原有 `实例数 × 块内实体数` 一次性预留不受 `kMaxExpandedEntities` 约束。最坏场景（预算允许的 100000 实例 × 块内大量实体）会一次性申请远超预算的巨量内存，可能触发 `bad_alloc`，与预算保护初衷相悖。
- **修复方式**：预留估算值钳制到 `[min(实例数, kMaxExpandedEntities)] × 每实例实体数` 且总量不超过 `kMaxExpandedEntities`，把峰值分配限制在预算实体上限内；`per-entity` 预算账本逻辑不变，正常图纸的预留精度不受影响。
- 修复后已重新执行 `cmake --build build --config Release --target Example1`，编译链接通过，产物 `bin/Release/Example1.pyd`。

**合并后含预算约束的时间复杂度：**

设 `N = nCols × nRows`（阵列实例数）、`E`（块内实体数）、`L`（块名字符串长度）、`d`（嵌套深度）。

| 项目 | 优化前 | 优化后（合并后） |
|---|---|---|
| 每点几何变换 | O(1)，6 乘 3 加 + 2 三角函数（角度非零） | **O(1)，4 乘 2 加**，无三角函数 |
| 单实例三角函数 | O(E) 次 cos/sin | **O(1)** 次（`Transform2D::fromInsert` 一次） |
| 阵列三角函数总数 | **O(E × N)** | **O(N)** |
| 单层阵列综合 | O(N × E + N × L + N × E) | O(N × E + N)（字符串拷贝 O(1)、坐标递推纯加法、reserve 钳制后扩容为 0 或按预算截断） |
| 嵌套阵列 | O(∏Nᵢ × E × d) | O(∏Nᵢ × E)（每层都省去三角函数与字符串拷贝） |

**新增预算约束后的最坏上界（重要）：**

`ExpansionBudget` 使展开过程成为**有界运行**：无论输入 DXF 多大、嵌套多深、阵列多极端，只要触达 `kMaxExpandedEntities = 100000` 或 `kMaxExpandedBlockInstances = 100000`，展开立即中止并报错。

- 实体输出上界：`O(kMaxExpandedEntities) = O(100000)`（常量）；
- 块实例上界：`O(kMaxExpandedBlockInstances) = O(100000)`（常量）；
- 因此最坏运行时间为 **`O(kMaxExpandedEntities)` 的常数倍**（每次实体生成 O(1) 变换 + 常量预算检查），嵌套深度受 `kMaxExpandDepth = 32` 限制。

即：合并后的复杂度从"理论无限展开、线性于输入总量"变为**线性于输出上限的常量界**——性能优化（低常数）与安全防护（有界输出）两者同时生效。恶意超大阵列不再造成内存或时间爆炸，而是快速返回明确的限额错误。

**遗留可优化点（未含本轮）：** reserve 钳制后，超出预算的 `nCols * nRows > kMaxExpandedEntities` 大阵列虽不会内存尖峰，但会在循环展开中被 `consumeEntities()` 逐实体拦截（最坏仍会遍历前 100000 个实例才中止）。若需更早失败，可在 `consumeArray()` 处按 `实例数 × 块实体数` 做一次前置估算拦截，见第 13 节回归测试与第 7.1 节测试基线建立后再评估。

### 20.6 SPLINE 解析路径优化（2026-08-01）

针对 `DxfReader::addSpline()` 的 SPLINE 回调，消除两层容器深拷贝并合并重复遍历，位置：`src/Example1/DxfParser.cpp`、`src/Example1/DxfData.h/.cpp`。

#### 优化前的问题

设 C = 控制点数、F = 拟合点数、K = 节点数。每根样条回调存在 **3 层 vector 深拷贝 + 2 次重复遍历**：

1. 调用点把 `ctrlPts` / `knots` / `weights` / `fitPts` 从 `DRW_Spline` 复制到局部容器（libdxfrw 对象无法转移所有权，这层不可避免）；
2. `DxfSpline` 构造按 `const&` 参数把 4 个容器再深拷贝一次（`m_ctrlPts(ctrlPts)` 等）；
3. `addSpline(const&)` / `push_back` 把整个 `DxfSpline` 再整体深拷贝一次，且内部 `spline.kind()` 又遍历 `ctrlPts` / `knots` 判断 construction；
4. `controllist` / `fitlist` 各被遍历两遍（先 isfinite 验证、再组装）。

单根样条开销为 `3 × O(C+F+K)` 元素拷贝 + `O(C+K)` 统计遍历。

#### 优化内容

1. **右值转移消除两层深拷贝**

   - `DxfData` / `DxfBlock` 新增 `addSpline(DxfSpline&&)` 移动重载，`push_back(std::move(...))`；
   - `DxfSpline` 新增右值构造（`std::vector&&` 参数），成员容器直接 `std::move` 转移所有权；
   - 回调中局部容器 `std::move` 进 `DxfSpline`，再 `std::move` 进 `addSpline`。

   结果：**3 层深拷贝降为 1 层**（仅 libdxfrw → 局部容器那层不可避免）。

2. **合并验证与组装为一遍遍历**

   - `knots`：原来数量校验、isfinite/单调校验、组装分三段；现 `reserve` 后边校验边 `push_back`，数量不符或非法立即返回；
   - `controllist`：原来先校验一遍再组装一遍；现边校验边组装；
   - `weights`（rational 时）：同理合并。

   每数组 2 遍遍历 → 1 遍。

3. **`kind()` 懒缓存**

   `SplineKind DxfSpline::kind()` 首次调用时计算并缓存到 `mutable` 成员。`DxfData::addSpline()` 统计 `splineKinds[spline.kind()]` 不再重复遍历 `ctrlPts` / `knots`，且块展开中 `recordGeneratedSpline(spline.kind())` 同样 O(1)。

#### 时间复杂度（每根 SPLINE 回调）

设 C = 控制点数、F = 拟合点数、K = 节点数。

| 项目 | 优化前 | 优化后 |
|---|---|---|
| 元素深拷贝 | **3 × O(C+F+K)** | **O(C+F+K)**（仅 1 层不可避免复制） |
| 验证 + 组装遍历 | controllist/fitlist 各 2 遍 | 各 1 遍 |
| kind 统计 | O(C+K) 遍历 | **O(1)**（懒缓存） |
| 单根合计 | ~3(C+F+K) + (C+F) + (C+K) | ~(C+F+K) + (C+F) |

解析 N 根样条的总复杂度从 `O(Σ3(Cᵢ+Fᵢ+Kᵢ))` 降为 `O(Σ(Cᵢ+Fᵢ+Kᵢ))`——大图纸（万级 SPLINE × 块实例化）常数因子降至 1/3，且统计路径全部 O(1)。对解析结果（坐标、节点、权重、标志、切向量）没有任何行为改变。
