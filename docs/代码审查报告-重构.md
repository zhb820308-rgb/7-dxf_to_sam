## 🚨 必须修复 (P0 - 阻断发布)

### P0-1: addLWPolyline 越界读取 — 恶意/畸形 DXF 文件导致崩溃

> **位置**: `src/Example1/DxfParser.cpp` 第 38, 50-51 行
> **严重度**: 🔴 高 — 可导致程序崩溃

**问题描述**:

```cpp
const int numVerts = data.vertexnum;   // line 38 — 来自 DXF 文件头部声明
...
for (int i = 0; i < numVerts; ++i) {   // line 50 — 以声明值为上界
    const DRW_Vertex2D& v = *data.vertlist[i];  // line 51 — 解引用可能越界
}
```

`data.vertexnum` 是 DXF 文件自己声明的顶点数，`data.vertlist` 是 libdxfrw 实际解析到的顶点列表。畸形文件可以声明 `vertexnum=100000` 但实际只有 2 个顶点，导致第 3 次迭代时 `vertlist[2]` 越界 → **段错误崩溃**。

老代码同样存在此问题，本次重构保留了它。既然在改这块代码，应当顺手修掉。

**修复建议**:

```cpp
const int numVerts = std::min(data.vertexnum, static_cast<int>(data.vertlist.size()));
if (numVerts < 2) return;
```

或者直接用 `data.vertlist.size()` 替代 `data.vertexnum` 作为循环边界。

## ⚠️ 建议优化 (P1 - 强烈建议)

### P1-1: s_nextId 全局计数器 — 非线程安全

> **位置**: `src/Example1/DxfData.cpp` 第 9 行
> **严重度**: 🟡 中 — 当前单线程使用不触发，但阻碍未来的并行化

**问题描述**:

```cpp
static int s_nextId = 1;
```

翻译单元级别的全局可变状态。`DxfEntity` 构造函数对其执行非原子的 `s_nextId++`。当前 SAM 插件单线程使用不会触发；但如果未来有批量并行导入需求，ID 会重复或丢失。

**重构建议**:

```cpp
#include <atomic>
static std::atomic<int> s_nextId{1};
```

### P1-2: tessellateBulgeArc 对极端 bulge 值无防御 — 已降级为 P2

> **位置**: `src/Example1/GeometryUtils.cpp` 第 60-61 行
> **严重度**: ⚪ 低 — 实际触发条件极苛刻，入口已有多层校验

**问题描述**:

```cpp
double centerDist = chord * (1.0 - bulge * bulge) / (4.0 * bulge);
```

函数入口只做了 `std::abs(bulge) < 1e-12` 的检测（微小值），但没处理 bulge 趋于无穷大的情况。

**降级分析**: 经过调用链追溯，`tessellateBulgeArc` 的唯一入口是 `tessellateLWPolyline`，其 bulge 值来自 `DxfParser::addLWPolyline()` → `DxfLWPolyline::isValid()` 已通过 `std::isfinite(b)` 拦截 NaN 和 Inf。一个极大但有限的 bulge（如 1e15）虽能通过验证进入函数，但只会导致数值精度极差的离散化而不会崩溃。这种 bulge 只会来自恶意/畸形 DXF 文件，属于“垃圾进、垃圾出”的范畴，不是 `tessellateBulgeArc` 的防御责任。

**结论**: 从 P1 降级为 P2，当前测试已覆盖正常 bulge 范围（0, ±0.414, 1.0, 2.414），无需额外修复。

### P1-3: DxfArc::isValid() 允许满圆弧通过 — 语义歧义

> **位置**: `src/Example1/DxfData.cpp` 第 105-112 行
> **严重度**: 🟡 中 — 不崩溃，但产生逻辑歧义

**问题描述**:

```cpp
&& (m_startAngle != m_endAngle);
```

这段代码意图拒绝零扫掠角的退化弧，但 `0.0 != 2π` 为 true，所以 `[0, 2π]` 的满圆弧通过验证。满圆弧应是 `DxfCircle`，不是 `DxfArc`。虽然 `tessellateArc` 的直接角度采样能生成完整圆（不会崩溃），但语义上产生了歧义：同一个圆可以用 Circle 或 Arc 表达，下游代码无法区分。

**重构建议**: 在 `isValid()` 中增加扫掠角合理性检查，或至少在注释中明确 `DxfArc` 允许的扫掠角范围。

### P1-4: LWPolyline 只支持 Z=0 — 丢失 DXF elevation

> **位置**: `src/Example1/DxfParser.cpp` 第 52, 67 行
> **严重度**: 🟡 中 — 功能缺失

**问题描述**: 顶点 Z 硬编码 0.0，`constZ` 硬编码 0.0。DXF LWPOLYLINE 的 elevation (组码 38) 被静默丢弃。这是一个**已知的设计取舍**而非 bug，但在代码和文档注释中未被标注为 TODO/Known Limitation。

**重构建议**: 加 `// TODO: 从 DRW_LWPolyline.elevation 读取 Z 值` 注释。

## ✅ 做得好的地方

1. **架构决策正确**: "解析存原始数据，转换时再离散" 是经典的责任分离，解决了旧代码解析器职责过重的问题。新增的 `DxfArc`/`DxfEllipse`/`DxfLWPolyline` 实体类型保留了原生几何语义，为后续扩展（如样条曲线）留下了干净的接口
2. **133 个测试、100% 通过率**: 覆盖了纯数学（31 个）、实体验证（42 个）、离散化逻辑（22 个）、集成 `convert()`（18 个）、真实 DXF 文件端到端管道（20 个）。特别是满椭圆回归测试直接命中了之前用户报告的生产 bug
3. **`normalizeSweep` 提取到 `GeometryUtils`**: 将之前隐藏在 .cpp 中的 file-static 函数提升为命名空间级公共 API，同时解决了可测试性和复用性问题
4. **`addSegments` lambda 消除重复**: `convert()` 中三个几乎相同的 7 行循环被压缩成 1 个 lambda + 3 个单行调用 — 教科书级别的 DRY 重构
5. **`tessellateArc` 改用直接角度采样**: 不再走 bulge 往返（圆心→端点→bulge→圆心→采样点），直接用已知圆心+半径做角度采样，消除了中间误差源且与 `tessellateEllipse` 结构一致
6. **防御性双保险**: 解析阶段 (`addArc`/`addEllipse`) 和数据模型层 (`isValid()`) 各自独立做验证，即使解析层漏了一个无效实体，`convert()` 阶段也会通过 `isValid()` 过滤掉
7. **ConversionEngine 方法可见性调整**: 将 `tessellate*` 和 `translate` 从 private 提升为 public static，使单元测试可以直接调用 — 这是务实的 TDD 设计选择，不牺牲封装性（它们本来就不依赖实例状态）
